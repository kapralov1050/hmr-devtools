# vite-plugin-pilot — обзор и сравнение с нашим плагином

> Источник: <https://github.com/2234839/vite-plugin-pilot> (53★, 5 форков, v1.0.36).
> Девиз автора: **«DevTools MCP, but from the inside»** — не CDP-снаружи, а код-инсайдер внутри страницы.

---

## 1. Что это

Vite-плагин + опциональный standalone-сервер, который даёт AI-агенту «глаза и руки» в **реальном** браузере разработчика (не Puppeteer/Playwright — без эмуляции). Агент может:

- читать состояние страницы (логи, ошибки, снимок DOM, маршрут, query, performance),
- исполнять произвольный JS в контексте страницы и получать результат,
- управлять страницей (клики/ввод/scroll по тексту и по индексу),
- получать выбранный пользователем элемент через Alt+Click с привязкой к исходнику,
- прокидывать промпт из браузера прямо в Claude Code session.

Два режима:

| Режим | Описание |
|---|---|
| **Vite Plugin** (рекомендуемый) | Автоинжект клиента в dev-страницу, `pnpm dev`, ноль настройки |
| **Standalone Server** | `npx pilot server` + `bridge.js` / Tampermonkey userscript — работает на любом сайте (включая prod) |

## 2. Возможности (фактически реализованные)

| Модуль | Что делает |
|---|---|
| **Log Collector** | Перехват `console.*`, `window.onerror`, `unhandledrejection`; батч-аплоад, маркер `data-v-pilot-*` |
| **Remote Exec** | Выполнение JS в странице, синхронный ответ (10–50 мс) + прицепом снапшот и логи |
| **Element Inspector** | Alt+Click → overlay с компонентом/источником/размерами; Alt+Scroll — переключение parent/child; Alt+RightClick — `code -g file:line` в VS Code |
| **Page Snapshot** | «compact» (~80 строк) формат: `tag#idx[val=V][check=…][type:T][ph=P][href:…][disabled] text` с авто-фокусом на область операции (±4 строки, дальше `·`) |
| **Source Locator** | `transform`-хук Vite, `magic-string` инжектит `data-v-pilot-file` / `data-v-pilot-line` в элементы `.vue`/`.html` |
| **Bridge** | Standalone-сервер: HTTP + SSE + WebSocket для WS-only клиентов |
| **Userscript** | Tampermonkey-скрипт для подключения к произвольным сайтам |
| **Multi-instance** | Несколько вкладок/окон, выбор по `instance:префикс` или `PILOT_INSTANCE` |
| **Channel Server** | Browser Alt+Click → MCP stdio → Claude Code session; fallback через `.pilot/channel-pending.txt` + `UserPromptSubmit` hook |
| **CLI** | `npx pilot {run, page, logs, status, server, bridge, userscript, help}` |

### Готовые хелперы в браузере (для `npx pilot run`)
- Текстовые: `__pilot_clickByText`, `__pilot_dblclickByText`, `__pilot_typeByPlaceholder`, `__pilot_setValueByPlaceholder`, `__pilot_selectValueByText`, `__pilot_checkByText` / `uncheckByText` / `checkMultipleByText`, `__pilot_keydownByText`, `__pilot_findByText`, `__pilot_waitFor`, `__pilot_waitEnabled`
- По индексу: `__pilot_click(i)`, `__pilot_dblclick(i)`, `__pilot_type(i,v)`, `__pilot_setValue(i,v)`, `__pilot_hover(i)`, `__pilot_scrollIntoView(i)`, `__pilot_getRect(i)`, `__pilot_check(i)`, `__pilot_uncheck(i)`
- Прочее: `__pilot_wait(ms)`, `__pilot_snapshot()`

> Особо: учитывает v-model и scheduler (Vue/React) — формы реально работают, в отличие от наивного `el.value = …`.

### 3.5 Технологии

- **Язык**: TypeScript 7 (`tsconfig.node.json` отдельно для Node)
- **Peer deps**: `vite >=5`, `magic-string` (опц.), `@vue/compiler-dom` (опц.)
- **Без рантайм-зависимостей** (только peer), движок `node >=18`
- **Сборка**: Vite-bundle + `write-inject-bundle.mjs` (сборка клиентской части в строку для инжекта)
- **Транспорт**: WS (HMR в dev-режиме), SSE (для standalone), HTTP (polling fallback, REST)
- **Vite hooks**: `configureServer` (HTTP middleware), `transformIndexHtml` (инжект), `transform` (source locator)

## 5. Что можем позаимствовать

### 5.1 Сразу — дёшево и высокоценно
1. **Compact snapshot** — единый читаемый формат `tag#idx[val=V][check=…][type:T][ph=P][href:…][disabled] text` вместо сырого HTML/a11y-дерева. Решает проблему «слишком много токенов» для агента.
2. **Фокус снапшота на области операции** — после клика/ввода отдавать только ±4 строки вокруг таргета, остальное сворачивать в `·`. Дешёвая фича, огромный выигрыш по контексту.
3. **Хелперы `__pilot_*`** в клиенте — особенно `clickByText`, `typeByPlaceholder`, `setValueByPlaceholder`, `waitFor`, `findByText`, `wait`. Сразу поднимают надёжность взаимодействия с v-model (Vue/React).
4. **Multi-instance** — `instanceId` в WS-handshake + фильтр-параметр `/__dev_exec?instance=…` + в `/__dev_logs?instance=…`. Тривиально, решает коллизию вкладок.
5. **Ограничение размера результата** — 100KB cap на сериализованный `eval` (наш сейчас неограничен).
6. **Hinter-секция `--- hint ---`** — когда агент делает DOM-операцию нативно (`document.querySelector(...).click()`), подсказать, что есть `__pilot_clickByText`. Мягко мигрирует на лучшие практики.

### 5.2 Среднесрочно
7. **Element Inspector** через `magic-string` в `transform`-хуке — `data-v-pilot-file` / `data-v-pilot-line` на узлах. Даёт jump-to-source из браузера и привязку элемента к компоненту.
8. **Alt+Click → AI-промпт** — пользователь тыкает в элемент → готовый промпт «поменяй это» с контекстом (компонент, источник, размер, текст, computed styles). Поднимает UX отладки на порядок.
9. **CLI-обёртка** (`npx pilot run '…' nopage instance:abc`) — даёт агенту короткие и предсказуемые команды вместо curl с экранированием query-параметров. Не обязательно, но удобно.
10. **Контекстные логи `--- context logs ---`** — N строк логов, предшествующих ошибке в `run`-режиме. Сильно помогает при разборе падений.

### 5.3 Долгосрочно / опционально
11. **Standalone-режим + Tampermonkey** — позволит дебажить и production-сайты. Не критично для нашего сценария (мы работаем с собственным dev-окружением), но расширяет применимость.
12. **Channel Server** (browser → Claude Code session) — зависит от того, используем ли мы Claude Code как рантайм-агента.

## 6. Преимущества нашего подхода (что у нас лучше)

1. **Скрытность канала** — наш трафик идёт **только** через HMR WebSocket; в Network-вкладке ничего не появляется. У pilot — HTTP POST `/__pilot/logs` и `/__pilot/result`, которые видны в DevTools и могут попасть в расширения/блокировщики.
2. **Меньше поверхности атаки** — нет отдельного SSE/HTTP-эндпоинта для логов/результатов, всё внутри существующего HMR-сокета.
3. **Кольцевой буфер + дедупликация** встроены в core, не зависят от внешней файловой системы.
4. **Фильтры на сервере** — `level`, `type`, `url`, `text`, `since`, `limit` query-параметры прямо в `GET /__dev_logs`. У pilot фильтрация — только на стороне CLI.
5. **Системные маркеры `session`/`truncate`** пробрасываются сквозь фильтры — агент видит границы сессий даже при фильтрации по уровню.
6. **Манифест возможностей** (`GET /__agent/manifest`) — у pilot его нет, они полагаются на статический `SKILL.md` в проекте. Манифест даёт динамическое описание tools с JSON-schema, не зависит от LLM-агента и его конфигов.
7. **Плагин не зависит от npm-пакета** — это in-tree код проекта; версия и поведение полностью под нашим контролем, нет внешней поверхности обновлений.

## 7. Резюме

`vite-plugin-pilot` — зрелый (53★, 1.0.36), production-ready аналог для Vite-проектов с упором на AI-агентов. Его сильные стороны — **UX** (compact snapshot, `__pilot_*` хелперы, Alt+Click, CLI, multi-instance) и **AI-tooling интеграция** (`SKILL.md`, auto-setup, Channel Server).

Наш плагин сильнее в **архитектуре канала** (HMR-only, манифест, фильтрация) и **инфраструктурных ограничениях** (без MCP, без внешних CLI). Прямое заимствование **compact snapshot + `__pilot_*` хелперов + multi-instance + 100KB cap** закрывает ~80% разрыва в функциональности за небольшое время, не ломая нашу HMR-архитектуру.

## 8. Вопросы и ответы

### 8.1 Чем полезно маркирование `data-v-pilot-file` / `data-v-pilot-line` и что такое Source Locator

**Source Locator** — это механизм, который в момент Vite-трансформации исходников (`.vue`, `.html`, `.jsx`) с помощью `magic-string` **инжектирует в DOM-узлы специальные data-атрибуты**:

```html
<button data-v-pilot-file="src/components/LoginForm.vue" data-v-pilot-line="42" class="btn">
  Войти
</button>
```

**Зачем это нужно:**
1. **Обратная навигация DOM → исходник.** Без этих атрибутов у агента/человека нет быстрого способа понять «какой файл/строка отрисовали эту кнопку». С ними можно сгенерировать ссылку `vscode://file/<abs-path>:42` и открыть редактор в нужном месте одной командой.
2. **Element Inspector** (Alt+Click) читает именно эти атрибуты, чтобы показать оверлей с компонентом и источником. Без Source Locator Inspector покажет только «button, class=btn, текст=Войти» — и агенту придётся угадывать компонент.
3. **Агенту в `run`-режиме** можно писать `document.querySelector('[data-v-pilot-line="42"]')` вместо хрупких текстовых/структурных селекторов — стабильнее при рефакторинге.
4. **Работает в реальном времени** — Vite пересобирает атрибуты при каждом HMR-обновлении, поэтому они всегда актуальны.

**Как это технически делается:**
- `transform`-хук Vite для `.vue` / `.html` файлов.
- Парсится template, для каждого корневого тега в AST есть позиция в исходнике.
- `magic-string` вставляет атрибуты в исходный код **до** того, как Vite его скомпилирует.
- Для Vue SFC учитывается смещение template-блока относительно файла.

**Нужно ли нам:** да, если планируем Element Inspector и jump-to-source. Это среднесрочная фича (см. §5.2). Без неё Alt+Click теряет половину пользы.

### 8.2 Как работает Element Inspector

**Пошаговый сценарий:**

1. **Активация режима.** Пользователь зажимает `Alt` → клиент (`client/element-inspector.ts`) ловит `keydown`, ставит флаг `inspectorMode = true` и регистрирует слушатели `mousemove` / `click` / `contextmenu`.

2. **Подсветка под курсором.** На `mousemove` (с зажатым Alt):
   - `document.elementFromPoint(x, y)` → целевой элемент.
   - Создаётся/перемещается оверлей `<div>` с `position: fixed`, `z-index: 2147483640`, `pointer-events: none` — обводит элемент рамкой + показывает мини-карточку (компонент, `data-v-pilot-file:line`, размер).
   - **Alt + Scroll вверх** → перейти к родителю; **Alt + Scroll вниз** → вернуться к ребёнку (как в `code-inspector-plugin`).

3. **Alt + Click (выбор).**
   - Клиент собирает `ElementInfo` (см. §3 в PLAN.md pilot): `tagName`, `className`, `rect`, `textContent` (≤200 символов), `sourceFile`, `sourceLine`, `componentName` (через `__vueParentComponent`), `domPath`, `computedStyles`.
   - Отправляет `POST /__pilot/inspect` на dev-сервер.
   - Сервер вызывает `prompt/generator.ts` → собирает готовый промпт с контекстом и пишет в `.pilot/selected-element.json` **или** пушит в Claude Code session через Channel Server.
   - Появляется плавающая панель с кнопками: «Скопировать промпт» (всегда работает) и «Отправить в Claude» (работает, если поднят Channel Server).
   - Через 8 секунд бездействия панель сама закрывается; ввод в textarea сбрасывает таймер.

4. **Alt + Right Click** → сразу выполняет `code -g <abs-path>:<line>` (jump в VS Code), минуя генерацию промпта.

**Чем полезно агенту (не только человеку):**
- Агент, получив файл `.pilot/selected-element.json`, точно знает, **что** пользователь имеет в виду — не нужно разбирать «ну вон та кнопка справа от логотипа».
- Привязка к `data-v-pilot-file:line` даёт прямое указание, **где** править.

**Нужно ли нам:** зависит от UX-сценария. Если агент работает в основном автономно — низкий приоритет. Если планируется интерактивная отладка с человеком (потыкал → агент поправил) — высокий.

### 8.3 Нужен ли нам Page Snapshot (он же compact snapshot)

**Важное уточнение:** Page Snapshot у pilot — это **не изображение**. Это компактное **текстовое** представление DOM, специально заточенное под LLM:

```
form#login-form[disabled] Войти
  input#email[type=email][ph="Email"]
  input#password[type=password][ph="Пароль"]
  button.btn-primary#submit[type=submit] Войти
  a.link[href=/forgot] Забыли пароль?
```

~80 строк текста, без скриншотов, без base64-картинок. Если ваша модель не умеет в изображения — это не блокирует, snapshot **текстовый**.

**Что даёт агенту:**
- **Видеть структуру страницы** без `eval('document.body.outerHTML')`, который может вернуть мегабайты и утопить контекст.
- **Индексы `#N`** для стабильных обращений: `__pilot_click(3)` вместо хрупких селекторов.
- **Атрибуты `[val=V]` / `[check=…]` / `[type:T]` / `[ph=P]`** — сразу видно состояние контролов (что в инпуте, что выбрано в select, какие чекбоксы отмечены).
- **Авто-фокус на области операции** — после клика snapshot показывает только ±4 строки вокруг таргета, остальное свёрнуто в `·`.

**Нужно ли нам:** да, и это одна из самых ценных вещей для заимствования (см. §5.1, пункт 1–2). Даже если модель не понимает картинки — она прекрасно читает такой текст. Без snapshot агенту приходится либо слать огромный HTML, либо гадать по «характерным» классам.

**Альтернатива, которую мы планировали в README** («снимок DOM / accessibility tree») — менее удобна: a11y tree многословнее и не несёт индексов, сырой DOM — слишком шумный. Compact-формат pilot — оптимум.

### 8.4 Как работает multi-instance и нужен ли он нам

**Как у pilot:**
1. При первом подключении браузера клиент генерирует свой `instanceId` (например, `131646c7`), регистрируется на сервере, получает `type`-метку: `[vite]` (через Vite-плагин), `[console]` (через `bridge.js` в консоли), `[userscript]` (через Tampermonkey).
2. Сервер хранит реестр инстансов в `.pilot/instances/<id>.json` (метаданные: `url`, `title`, `type`, `lastSeen`).
3. Все WS-команды (`exec`, `inspect`) рассылаются **всем** инстансам, но ответ помечен `instanceId` отправителя.
4. CLI / HTTP-эндпоинты принимают `instance:префикс` или `?instance=1316` — фильтруют таргет.
5. `npx pilot status` выводит список: `131646c7 [vite] localhost:5173 — Login page (← current)`.

**Зачем нужно:** у разработчика может быть открыто 5 вкладок (admin, логин, дашборд, storybook, отдельная фича). Без multi-instance `exec('document.title')` вернёт ответ от **первой подключившейся** вкладки, а не от той, в которой агент работает.

**Нужно ли нам:** **да, низкая цена — большой выигрыш.** Сейчас у нас одна вкладка выигрывает по факту подключения, остальные её логи перетирают. Реализация:
- Генерировать `instanceId` в `devLogger/execChannel.ts` при первой инициализации (например, `${Date.now()}-${Math.random().toString(36).slice(2,8)}`).
- Класть его в каждое HMR-сообщение (`dev-log`, `dev-exec-result`).
- На сервере — `Map<instanceId, RingBuffer>` вместо одного буфера.
- В HTTP-эндпоинтах — `?instance=…` для фильтра.
- В `/__agent/manifest` — список активных инстансов с метаданными (url, title, lastSeen).

### 8.6 §3.4 — Является ли `npx pilot run` тем самым «манифестом»

**Нет, это разные вещи, путать не стоит:**

| Что | Что делает |
|---|---|
| **`npx pilot run 'код'`** | **Исполнитель команд.** Агент отправляет JS в браузер, получает результат + логи + снапшот. Это **action**, а не декларация. |
| **`SKILL.md` / `SETUP.md`** (статические файлы в проекте) | **Декларация возможностей** для IDE/агента. Текстовое описание команд, хелперов, форматов. Читается LLM при старте сессии. Это **у pilot и есть аналог «манифеста»**, но не runtime-endpoint, а статика. |
| **Наш планируемый `GET /__agent/manifest`** | **Runtime-манифест** — JSON-эндпоинт с актуальными `name`, `version`, `capabilities[]`, `tools[]` со схемами, `examples`, `system_hint`. Агент обнаруживает возможности динамически, в момент, когда они нужны. |

**Сравнение подходов:**

| | pilot (SKILL.md) | наш (манифест) |
|---|---|---|
| Формат | Markdown | JSON + JSON-schema |
| Где лежит | В репозитории плагина, копируется в проект через SETUP.md | Отдаётся HTTP-эндпоинтом плагина |
| Версия/порт | Могут расходиться с реальностью (текст надо обновлять) | Всегда актуальны (плагин сам отдаёт) |
| Зависит от MCP/IDE | Да (для работы как skill нужен Claude Code / Cursor / Windsurf) | Нет — работает с любым агентом через `curl` |
| Поддержка инструментов | Текстовое описание, нет машинно-читаемой схемы | JSON-schema для каждого tool — можно автогенерировать клиент |

**Вывод:** манифест (`GET /__agent/manifest`) — это наша **замена** `SKILL.md` для случая, когда MCP/skill-регистрация недоступна. По сути более слабая, но более переносимая версия того же концепта.

### 8.7 Нужен ли нам standalone-режим (чтобы читать прод)

**Что даёт standalone:**
- Отдельный HTTP-сервер `npx pilot server`, не привязанный к Vite.
- К нему подключаются Tampermonkey-скриптом или `bridge.js` из консоли — работает на **любом** сайте, включая prod.
- Агент может дебажить prod-страницу, на которой нет нашего Vite-плагина.

**Почему у нас это, скорее всего, не нужно:**

1. **Агент не может фетчить страницы.** Если агенту запрещено делать HTTP-запросы к произвольным URL (кроме локалхоста нашего dev-сервера), то он не может ни открыть prod-страницу, ни получить оттуда данные. Standalone-режим дебажит **браузер пользователя**, а не страницы, которые агент сам открывает — поэтому если агент не управляет браузером напрямую, ему это бесполезно.

2. **Наш сценарий — собственный dev-окружение.** Мы разрабатываем конкретный проект. Прод-баги воспроизводятся в dev (или в feature-ветке с моками). Запустить `pnpm dev` и подцепиться — дешевле, чем объяснять пользователю «установи Tampermonkey, открой прод, вставь userscript».

3. **Отдельный сервер = отдельная поверхность атаки и поддержки.** Плюс ещё один процесс, который надо запускать/конфигурировать.

4. **Наш плагин и так невидим в Network (HMR-only).** Pilot в standalone светит HTTP-эндпоинты `/__pilot/*` — это противоречит нашему принципу «не светиться».

**Когда бы пригодилось:** если появится задача «AI-агент помогает пользователю на произвольном сайте» (не нашем) — тогда да. Сейчас — нет.

### 8.8 AI-tooling интеграция у pilot — нужна ли нам

**Что у pilot:**
1. **`SKILL.md`** — файл с YAML-фронтматтером (`name`, `description`), который Claude Code / Cursor / Windsurf подхватывают как skill. Агент в начале сессии получает инструкцию «как пользоваться pilot».
2. **`SETUP.md`** — инструкция для AI, которую сам AI читает и применяет: установить плагин, дописать usage-гайд в `CLAUDE.md` / `.cursorrules`, добавить `.pilot` в `.gitignore`.
3. **Channel Server** — прямое прокидывание промпта из браузера в Claude Code session через MCP stdio (`@modelcontextprotocol/sdk`). Fallback — файл `.pilot/channel-pending.txt` + `UserPromptSubmit` hook.
4. **CLI `pilot`** — удобные короткие команды, которые проще вызывать, чем curl с экранированием.

**Что из этого полезно нам, а что нет:**

| Фича pilot | Нам | Почему |
|---|---|---|
| `SKILL.md` (статический) | Нет | У нас запрещены MCP/skill-регистрации; наш манифест решает ту же задачу динамически. |
| `SETUP.md` (auto-setup) | Частично | Плагин не npm-пакет, ставить ничего не надо. Но идея «пусть AI сам допишет строку в AGENTS.md при первой активации» — берём (см. §2.4 нашего README). |
| Channel Server | Нет | MCP stdio не разрешён в нашем контуре. Fallback через файл теоретически возможен, но для этого нужно, чтобы Claude Code был рантайм-агента (у нас — другое). |
| CLI `pilot` | Опционально | Удобно для интерактивной работы; не критично, если агент работает curl-ом. Можно сделать минимальный CLI позже. |

**Наш подход (манифест) — это не «хуже», а «иначе»:**
- Pilot регистрирует инструменты **заранее** (через skill-файл).
- Мы публикуем инструменты **по запросу** (через HTTP-эндпоинт).
- В обоих случаях LLM получает описание capabilities. Разница в том, **когда** и **откуда** это описание приходит.

**Итого:** манифеста достаточно. Pilot'овская AI-tooling интеграция — это про экосистему Claude Code; у нас другие ограничения, поэтому своё решение (манифест + AGENTS.md).

### 8.9 Сериализация результата — подробнее

**У pilot:**
```ts
// грубо, по PLAN.md
const max = 100 * 1024;
const serialized = JSON.stringify(result);
if (serialized.length > max) {
    return { error: 'Result exceeds 100KB', truncated: true };
}
```
Плюс `execTimeout = 5s` по умолчанию (защита от бесконечных циклов).

**У нас** (см. `devLogger/execChannel.ts`):
```ts
function serialize(value: unknown): string {
    try {
        return JSON.stringify(value) ?? String(value);
    } catch {
        return String(value);
    }
}
```
Никаких лимитов ни на размер, ни на время выполнения. Наш timeout есть только на стороне сервера в `devBrowserLogs.ts:223` (10s по умолчанию, переопределяется `?timeout=`), но это время **ожидания ответа от браузера**, а не чистого исполнения кода.

**Что лучше доработать у нас:**

| Что | Сейчас | Риск | Рекомендация |
|---|---|---|---|
| **Max size результата** | Нет | `JSON.stringify(bigTree)` может вернуть 10 МБ → забить контекст агента, лечь OOM | Cap 100–500 KB на сериализованный `value`, при превышении — `{ ok: true, truncated: true, preview: '...' }` |
| **Exec timeout на клиенте** | Нет (только серверный 10s) | `while(true){}` в `eval` — браузер зависнет, агент зависнет по своему таймауту | `Promise.race` с таймером на клиенте, abort через `Error('Execution timed out')` |
| **Циклические ссылки** | `JSON.stringify` бросает → catch → `String(value)` (строка вида `[object Object]`) | Теряется полезный сигнал | Возвращать `{ ok: false, error: 'Cyclic structure', hint: 'return JSON-safe value' }` |
| **Function/Map/Set** | `JSON.stringify({map: new Map()})` → `'{}'` — тихо ломается | Агент не понимает, почему пусто | Возвращать `{ ok: false, error: 'Non-serializable: Map', hint: 'use Array.from(map.entries())' }` |

**Что НЕ надо менять:**
- Сам факт, что мы сериализуем через `JSON.stringify` — нормально, агенту нужен парсабельный JSON.

### 8.10 Какой дедуп / rate-limit лучше — у нас или у pilot

**Pilot:**
- Батч-флаш раз в `flushInterval` (по умолчанию 1000 мс).
- `maxBufferSize` (по умолчанию 200) — лимит размера буфера на клиенте.
- Никакой дедупликации **одинаковых** сообщений — просто буфер с отсечкой по размеру.
- HTTP-эндпоинт `/__pilot/logs` принимает массив, дописывает в файл.

**У нас** (см. `devLogger/core.ts`):
- Ring-buffer на сервере, 5000 записей, при переполнении отрезаем половину и пишем маркер `truncate`.
- **Дедупликация одинаковых подряд сообщений** через `flushDuplicates` / `resetDedupState`.
- Батч-отправки нет (шлём по мере появления через HMR WS).
- HTTP-эндпоинт `/__dev_logs` фильтрует через query-параметры.

**Сравнение:**

| Аспект | Pilot | Мы | Кто лучше |
|---|---|---|---|
| Защита от шторма одинаковых логов | Нет (всё льётся в буфер) | Да (`flushDuplicates`) | **Мы** |
| Защита от переполнения памяти | Да (maxBufferSize на клиенте) | Да (maxEntries на сервере + truncate-маркер) | Паритет, наш вариант информативнее для агента |
| Backpressure при потере WS | Теряются (буфер на клиенте сбрасывается после отправки) | Теряются (буфер на сервере, при перезапуске `buffer.length = 0`) | Паритет |
| Rate-limit отправки | Да (`flushInterval: 1000`) | Нет (отправляем сразу) | **Pilot** — бережёт WS и сервер, если логов очень много |
| Агентские фильтры | Только на стороне CLI (`nopage`, `nologs`) | На стороне сервера (`level`, `type`, `url`, `text`, `since`, `limit`) | **Мы** — меньше трафика, меньше токенов |

**Что стоит заимствовать у pilot:** добавить **rate-limit на клиенте** (батч по 100 мс или по N сообщений), если окажется, что HMR WS захлёбывается при шторме console.log-ов. Пока не критично.

**Что у нас лучше:** дедуп + серверные фильтры + системные маркеры сессии. Не трогать.

### 8.11 Какие пост-фильтры лучше — у нас или у pilot

**Pilot (CLI-уровень):**
```bash
npx pilot run 'code'             # result + logs + snapshot
npx pilot run 'code' nopage      # result + logs
npx pilot run 'code' nologs      # result + snapshot
npx pilot run 'code' nopage nologs  # только result
```

Плюс `npx pilot logs` отдельно для чтения файла логов.

**Мы (HTTP query-параметры в `GET /__dev_logs`):**
```

?type=network
?url=/api/users
?text=Unauthorized
?since=2026-09-17T10:00:00Z
?limit=100
```
Комбинируются (AND). Системные маркеры (`session`, `truncate`) проходят сквозь фильтры.

**Сравнение:**

| Возможность | Pilot | Мы |
|---|---|---|
| Фильтр по уровню | Нет (приходят все) | `?level=` |
| Фильтр по типу | Нет | `?type=` |
| Фильтр по URL | Нет | `?url=` (substring по `url` и `netUrl`) |
| Полнотекстовый поиск | Нет | `?text=` (по msg, stack, netUrl) |
| Фильтр по времени | Нет | `?since=` (ISO timestamp) |
| Лимит выборки | Нет | `?limit=` (последние N) |
| Исключение снапшота из `run` | `nopage` (CLI) | Не применимо (у нас нет встроенного snapshot) |
| Исключение логов из `run` | `nologs` (CLI) | Не применимо (у нас лог-эндпоинт отдельный от exec) |

**Вывод:** наши фильтры **значительно мощнее**. Агент может одной командой получить «все 5xx по `/api/users` за последние 5 минут» — у pilot такого нет, пришлось бы `cat .pilot/latest-errors.log | grep … | tail`.

**Что стоит заимствовать:** добавить к нашим фильтрам флаг `nopage` в ответ `exec`-эндпоинта (когда появится snapshot — убрать его из дефолтного ответа, чтобы не заливать контекст). Это аналог pilot'овского мода.

### 8.13 Нужен ли сырой DOM-снимок в дополнение к compact snapshot

**Да, нужен, и это ортогональная фича к compact snapshot.** Compact — для экономии токенов и стабильных обращений по индексу; сырой DOM — для диагностики анимаций/переходных состояний.

**Что теряется в compact-формате pilot (и почему это критично для нас):**

| Что | Compact snapshot | Сырой DOM |
|---|---|---|
| Текущий текст ноды | ✅ | ✅ |
| Базовые атрибуты (`val`, `check`, `type`, `ph`, `href`, `disabled`) | ✅ | ✅ |
| Произвольные `data-*` атрибуты (например, `data-state="opening"`) | ❌ | ✅ |
| Классы в полном составе (включая динамические: `.modal--entering`, `.btn--loading`) | ❌ (показывает только интерактивные классы) | ✅ |
| Inline-стили (`style="transform: translateX(-100%)"`) | ❌ | ✅ |
| Computed styles (текущие значения после CSS-каскада и анимаций) | ❌ | ✅ |
| Активная CSS-анимация / transition (`animation-name`, `animation-play-state`, `transition-duration`) | ❌ | ✅ |
| Видимость / позиция (`visibility`, `opacity`, `transform` matrix) | Только rect | ✅ |
| Соседние ноды, контекст | ±4 строки, остальное `·` | Полное дерево |

**Почему это особенно важно при большом количестве анимаций:**

1. **Промежуточные состояния видны только в DOM.** Класс `.modal--enter-active` существует доли секунды во время transition. Compact snapshot, снятый через секунду после открытия модалки, его уже не покажет. Сырой DOM по запросу агента — покажет.
2. **Computed styles содержат результат анимации.** Нужно увидеть «на каком кадре сейчас элемент» (transform matrix, opacity 0.7) — это доступно только через `getComputedStyle()`, compact обрезает.
3. **Атрибуты состояния фреймворка.** Vue/React часто пишут `data-state`, `data-testid`, `aria-*`, `data-radix-*`, `data-framer-*` — по ним агент понимает, что анимация в процессе, какой сейчас шаг перехода, был ли клик во время анимации.
4. **Диагностика «дёргается» / «мигает».** Чтобы понять причину, нужно сравнить два снимка DOM с интервалом в 100 мс и увидеть, какие классы/style менялись — compact для этого непригоден.

**Как реализовать рядом с compact (не вместо):**

Добавить отдельный эндпоинт, например `GET /__agent/dom`:

```
GET /__agent/dom?selector=.modal&depth=10&attrs=all&styles=computed
```

Возвращает JSON:
```json
{
  "selector": ".modal",
  "matches": 1,
  "tree": [{
    "tag": "div",
    "attrs": { "class": "modal modal--entering", "data-state": "opening", "aria-hidden": "false", "style": "transform: translateX(0)" },
    "computed": { "transform": "matrix(1, 0, 0, 1, -42, 0)", "opacity": "0.7", "animation-name": "modalEnter" },
    "children": [...]
  }]
}
```

**Опции:**

| Параметр | Назначение |
|---|---|
| `selector` | CSS-селектор; если нет — отдаём `document.body` |
| `depth` | Ограничение глубины рекурсии (по умолчанию 5, чтобы не утопить ответ) |
| `attrs` | `all` / `interactive` / `none` — какие атрибуты включать |
| `styles` | `none` / `inline` / `computed` — какие стили включать |
| `viewportOnly` | `true` — только элементы в viewport (экономия размера) |
| `maxSize` | Cap на размер JSON-ответа (по умолчанию 500 KB) |

**Триггерный режим (особенно ценно для анимаций):** ~~не нужен на текущем этапе~~ — отложен, помечен как «избыточно». Если позже потребуется отлаживать конкретные переходные анимационные баги, можно добавить точечно. Сейчас хватает разовых снимков по запросу агента.

```
POST /__agent/dom { "trigger": "selector", "value": ".error-banner", "capture": { "before": 1, "after": 3, "intervalMs": 100 } }
```

Браузер снимает N снимков с заданным интервалом вокруг момента, когда `selector` появится/исчезнет. Возвращает массив — **временной ряд DOM-состояний**. Это именно то, что нужно для отладки анимационных багов.

**Производительность:**

- `getComputedStyle()` на каждый узел — дорого. Делаем **только по запросу** (по конкретному selector), не по умолчанию.
- Рекурсия с лимитом `depth` и cap `maxSize`.
- Для trigger-режима — клиент сам себе шедулит снимки и стримит через WS (или буферизует и отдаёт массивом).
- Compact snapshot остаётся дефолтным ответом `run`; сырой DOM — отдельный запрос, когда агент подозревает анимационный баг.

**Связь с compact snapshot:** compact остаётся «дефолтным состоянием страницы» (быстро, дёшево, для большинства задач). Сырой DOM — «микроскоп» для конкретных анимаций/переходных состояний. Оба дополняют друг друга, не конкурируют.
